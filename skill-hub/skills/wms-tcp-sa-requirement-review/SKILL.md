description: ช่วยงานบทบาท System Analyst (SA) ในโครงการ WMS ของบริษัท ที.ซี.พี. อินดัสทรี้ จำกัด โดยเฉพาะด้านการตรวจสอบ วิเคราะห์ และอนุมัติเอกสาร System Requirement Specification (SRS) เพื่อยืนยันว่า Requirement ที่เขียนไว้ตรงกับความต้องการของลูกค้าและครบถ้วนตามขอบเขตระบบ  **ใช้สกิลนี้เมื่อ:** - ผู้ใช้สวมบทบาท SA ต้องการตรวจทาน (review) เนื้อหาเอกสาร SRS ก่อนอนุมัติ - ผู้ใช้ต้องการเช็คว่า Requirement แต่ละข้อครบถ้วน ไม่คลุมเครือ และสอดคล้องกับ Flow ธุรกิจจริงหรือไม่ - ผู้ใช้ต้องการช่วยแตก Requirement เป็น User Story / Use Case / Test Case อ้างอิงจากแต่ละ Module ในเอกสาร - ผู้ใช้ต้องการตรวจสอบความสอดคล้อง (traceability) ระหว่าง Requirement กับ Flow งาน (Inbound/Outbound/Inventory) - ผู้ใช้ต้องการสรุปจุดที่ Requirement ยังไม่ชัดเจนหรือขาดหายไป เพื่อนำไปสอบถามลูกค้า/ผู้ใช้งานเพิ่มเติม ก่อนเซ็นอนุมัติ
---

1. **ชี้แจงขอบเขตบทบาทให้ชัดเจน** เอกสาร SRS ระบุว่า SA มีหน้าที่หลักคือ**อนุมัติ (Approve)** เอกสาร SRS เพื่อยืนยันการยอมรับ Requirement ของลูกค้า ไม่ใช่ผู้ใช้งานปฏิบัติการในระบบ WMS (ไม่มีสิทธิ์เมนูคลังสินค้าโดยตรงตามที่ระบุในเอกสาร)

2. **เมื่อช่วยตรวจทาน Requirement ให้ตรวจสอบตามเกณฑ์นี้:**
   - **ความครบถ้วน (Completeness):** แต่ละ Module (01-11) มีการระบุ Input/Process/Output ชัดเจนหรือไม่
   - **ความสอดคล้อง (Consistency):** Requirement ในแต่ละ Module ขัดแย้งกันเองหรือไม่ เช่น บทบาทผู้รับผิดชอบซ้ำซ้อนหรือขาดหาย
   - **ความสามารถตรวจสอบได้ (Testability):** Requirement เขียนในลักษณะที่นำไปออกแบบ Test Case ได้หรือไม่
   - **Traceability:** Requirement แต่ละข้อเชื่อมโยงกับ Flow ธุรกิจ (PR→PO→Check In→Put Away หรือ Quotation→SO→Pick→Packing→DO) ได้หรือไม่

3. **ใช้โครงสร้าง Module อ้างอิงเดียวกับทีมธุรกิจ** (Module 01 Master Data, 02 Inbound, 03 Outbound, 04 Return, 05 Internal Transfer, 06 Warehouse Transfer, 07 Stock Count, 08 Add-on, 09-11 System Features) เพื่อให้ตรวจทานได้ครบทุกหมวดไม่ตกหล่น

4. **เมื่อถูกขอให้แตก Requirement เป็น User Story** ให้ใช้รูปแบบ:
   `ในฐานะ [บทบาท] ฉันต้องการ [ทำอะไร] เพื่อที่จะ [ผลลัพธ์ทางธุรกิจ]`
   พร้อมระบุ Acceptance Criteria อย่างน้อย 2-3 ข้อต่อ User Story

5. **เมื่อถูกขอให้ออกแบบ Test Case** ให้ระบุ: Test Case ID, Module ที่เกี่ยวข้อง, ขั้นตอนทดสอบ, ผลลัพธ์ที่คาดหวัง (Expected Result), และเงื่อนไข Pass/Fail

6. **เมื่อพบจุดที่ Requirement ไม่ชัดเจนหรือขาดหาย** ให้สรุปเป็นรายการคำถามที่ควรสอบถามผู้ใช้งาน/ลูกค้าก่อนอนุมัติ แทนที่จะสมมติคำตอบเอง

7. **ก่อนสรุปว่า Requirement "พร้อมอนุมัติ"** ให้เช็คย้อนกลับว่าครอบคลุมทั้ง 3 มิติ: Flow การทำงาน (Flow A/B/C), บทบาทผู้ใช้งาน (Admin/คลัง/ผลิต/ขาย/จัดซื้อ/บัญชี/QC), และ Integration (Express, MRP, Similan Ai)

8. **หากคำถามเกี่ยวกับสิทธิ์การเข้าถึงเมนูของ SA หรือรายละเอียดที่เอกสารไม่ได้ระบุ** ให้แจ้งตรงไปตรงมาว่าเอกสาร SRS ฉบับนี้ไม่ได้ระบุสิทธิ์การเข้าถึงของบทบาท SA ไว้ และแนะนำให้สอบถามทีมงานที่เกี่ยวข้องเพื่อยืนยัน
